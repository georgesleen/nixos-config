# gs-pi4 media pipeline

Workarounds and diagnosis notes for the nixflix stack on gs-pi4.
The media config itself lives in the private `nixos-pi4` flake input.

The stack accepted requests and downloaded nothing for weeks. Every cause was silent: units stayed green throughout. `media-health.nix` now checks the whole chain hourly and reports to the Homepage tile; its decision half (`media-health.sh`) has a fixture per failure below, so each one goes red if reintroduced.

- `nixflix.nix` `seerr.radarr`/`seerr.sonarr`: re-declaring a Jellyseerr instance replaces the module's whole default attrset, so `apiKey` **and** `activeDirectory` have to be restated. Omitting the latter let it fall back to the submodule default `/tv`, which no arr has; Sonarr rejected every add and each request silently went FAILED. Same trap for `activeProfileName`: unset, Seerr picks the arr's *first* profile, the stock "Any" (CAM, TELESYNC, BR-DISK, uncapped Remux), which is how a 53.7 GB remux and a TELESYNC landed.
- `nixflix.nix` `prowlarr.config.applications`: `lib.mkAfter` is `mkOrder`, not a priority, so it does **not** merge with the module's `mkDefault` list; any definition replaces it wholesale. Adding LazyLibrarian therefore deleted the Sonarr and Radarr entries, Prowlarr's indexers never synced to either arr, and both ran on stale leftovers (Radarr down to one indexer). List all apps explicitly; adding a fourth means restating all four.
- `nixflix.nix` `radarr.quality_profiles.min_format_score = 0`: TRaSH's SQP-1 ships `minFormatScore = 1000`, tuned for private trackers whose releases carry the labels those points come from. Against this public indexer the best release scores 185, so **0 of 100** releases were approved and nothing downloaded at all.
- `nixflix.nix` sonarr `custom_formats` x265 score 0: TRaSH scores `x265 (HD)` at -10000 to keep WEB re-encodes out of an x264 library. This box has no transcoding (clients direct-play HEVC) and a small disk, where a 3.75 GB x265 season pack beats the same season at 14.47 GB. The size minimums were already lowered "so x265 WEB passes"; the format score still rejected every one, including the best-seeded packs.
- `arr-quality-guard.nix` `cap` must equal the recyclarr cap in `nixflix.nix`: the guard runs hourly and recyclarr nightly and on every deploy, so a mismatch has them rewriting the same fields against each other forever (briefly 30 vs 60). Same reason `recyclarr.onSuccess` chains the guard: recyclarr leaves tiers it does not manage unlimited (13 Sonarr tiers went null on each deploy), and waiting for the hourly tick left a window where nothing was capped.
- `arr-quality-guard.nix` `season_pack_pref`: public trackers barely carry single episodes of an older show (per-episode searches returned "0 reports" for 61 and 52 episodes while complete packs sat there). Two things blocked packs: `Bluray-1080p` ranked below the `WEB 1080p` group so a pack read as a downgrade, and a pack scored ~0 against a WEB single's ~1700. Folding BluRay into that group and scoring a local "Season Pack" format above the WEB tiers fixes both. Bounded, not a loop: after the pack imports every episode carries its score. `reset_unmatched_scores.except` lists "Season Pack", but **that exemption does not actually work and never did**: recyclarr validates `except` against the guide's own format names, logs `has invalid CF names: Season Pack, Oversized, Extended Cut, Raw (No Subs), x265 (HD), LQ`, and resets the scores anyway (confirmed 2026-09-11). What really holds all six is the guard itself re-asserting them through `recyclarr.onSuccess`. Keep the guard; do not trust the `except` list.
- `nixflix.nix` `jellyfin.libraries` Movies/Shows trickplay + chapter extraction off: **this, not downloading, is what saturates the Pi.** Both run ffmpeg over every file in the library, the same class of load the box refuses to do for transcoding. Courses and YouTube were given these off from the start; Movies and Shows kept them. When ~200 imports landed on 2026-09-03 trickplay went into a rolling full-library sweep: I/O pressure sat at **95%** for over an hour, load near 30, ffmpeg logging "Trickplay process unresponsive" and retrying, and the Pi repeatedly unreachable over ssh and every arr port. Turning the four flags off took load 27.9 to 4.4 and I/O pressure 95% to 4% within minutes. `jellyfin-bg-pause.nix` does **not** cover this: it SIGSTOPs the batch jobs only while something is streaming, so with nobody watching the sweep runs flat out. Note the library flags apply through `jellyfin-libraries.service` over the API and do **not** restart Jellyfin, so an in-flight sweep keeps running until Jellyfin is restarted; the config change alone looks like it did nothing.
- When gs-pi4 looks "wedged" (sshd accepting TCP but failing at banner exchange, arr ports refusing), check `/proc/pressure/io` and `pgrep -a ffmpeg` **before** blaming downloads or a deploy. Both of those are real contributors but neither sustains 95% I/O on its own.
- `nixflix.nix` `prowlarr-downloadclients` ExecStartPre: any deploy that rewrites `qBittorrent.conf` restarts qBittorrent, and this unit then PUTs the download client while the WebUI is still starting. qBittorrent answers 400, the unit burns its 5 internal retries in 5 seconds, and the whole activation fails; Prowlarr is left with a stale client entry until someone restarts the unit by hand (hit twice on 2026-09-02). Gated on `192.168.15.1:8282/api/v2/app/version` answering, which is unauthenticated from the veth subnet. Same shape as the `seerr-setup` gate directly above it.
- `arr-jellyfin-notify.nix`: the arrs shipped with **no notifications at all**, so nothing told Jellyfin an import had happened and the whole request-to-watchable time rested on inotify. The libraries do set `EnableRealtimeMonitor`, but `LibraryMonitorDelay` is 60s, the watcher is easy to miss on a busy USB-backed btrfs tree, and Jellyfin's scheduled library scan here has **`Triggers: null`**, so nothing sweeps up a dropped event: a missed file simply never appeared until someone scanned by hand. This unit ensures a MediaBrowser notification on both arrs (targeted library update on import, far cheaper than a scan on a Pi). Written as an idempotent oneshot because nixflix models root folders, indexers and clients but not notifications. Deliberately no scheduled full scan was added: a full sweep is expensive on this I/O-bound box and the notification covers the import path.
- **Proving the Jellyfin notification works needs request logging, and this is a trap worth remembering.** At Jellyfin's default Info level an API-triggered library update logs *nothing*, so the only visible refresh is the `IO.LibraryMonitor` line the inotify watcher emits ~60s later anyway. Reading that log will convince you the notification is dead when it is fine. Sonarr's own `/notification/test` is equally useless: it only calls `POST /Notifications/Admin`, which 404s on Jellyfin (that is the "Unable to send notification to Emby" warning) and never exercises `updateLibrary`. To settle it, write a `logging.json` next to `logging.default.json` with `Microsoft.AspNetCore` at `Information` **and restart Jellyfin** (it reads that file only at startup, so editing it changes nothing on a running server), then watch a real import. Proven working 2026-09-03: import at 10:37:47, `POST /Library/Media/Updated` → **204 at 10:37:48.6** (0.9s), watcher following at 10:38:49 (62s). Remove the `logging.json` and restart again afterwards; it is an unmanaged file in a Nix-managed tree.
- `arr-jellyfin-notify.nix` `canon`: comparing the desired notification against the stored one needs a **projection**, or the unit rewrites both arrs on every run. Three things differ that are not ours: the schema carries `presets` while the stored record carries `id`; field entries carry helpText/type metadata; and the arrs return any field whose `privacy` is not `"normal"` as an **8-character mask**, so a 32-character API key never equals what is read back. That last one is the trap; the first two are easy to spot and still leave the bug.
- `nixflix.nix` `IgnoreSlowTorrentsForQueueing = false`: with it on, `MaxActiveDownloads` stops being a limit. A torrent still fetching metadata downloads at 0 B/s, so once `SlowTorrentsInactivityTimer` elapses it counts as "slow", stops counting as active, and qBittorrent starts another; adding many at once cascades through that gap. A library-wide search grabbed 15 releases and 19 ran at once against a limit of 5, taking the Pi to load 29 and I/O pressure 77% (2026-09-02): sshd failed at banner exchange and every arr port stopped accepting for ~15 min. The original reason for the flag is covered better now by Prowlarr's `appMinimumSeeders` 3 at grab time and decluttarr for stalled torrents. `MaxActiveTorrents` also had to go 12 to 200, since it counts seeders and was starving the download slots.
- `nixflix.nix` `config.radarr.radarr.custom_formats` x265 (HD) score 0: the same override Sonarr already had, which Radarr never got, so films kept TRaSH's -10000. It sank the best-seeded release of every stuck movie (The 40 Year-Old Virgin at 1.8 GB with 126 seeders, La La Land at 2.8 GB with 85), and the x264 alternatives left were all over the size ceiling, so the score and the cap rejected the whole list between them: 0 approved releases each. Zeroing it took La La Land 0 to 3 accepted, Mulan 0 to 2, The 40 Year-Old Virgin 0 to 3 (2026-09-02). **Radarr and Sonarr publish different trash_ids for the same format name** (`dc98083864ea246d05a42df0d05f81cc` vs `47435ece6b99a0b477caf360e79ba0bb`); the wrong one only logs `[WRN] Invalid trash_id` and silently applies no score, so check that line in the recyclarr journal after any custom-format edit. LQ is deliberately left negative for films: there it mostly means YIFY, and at `preferred = 18` a 1.2 GB YIFY rip would outrank a good 3.8 GB encode.
- Diagnosing "nothing was grabbed" in an arr: the per-reason rejection histogram **lies**. A release carries several rejections at once and a public indexer's long tail is mostly dead torrents, so "Not enough seeders" dominates the count and reads as "this title is unseeded" even when the well-seeded releases are all failing for an unrelated reason. Sort by seeders and read the rejections on the *top* few instead; that is what turned "these movies are genuinely unseeded" into the x265 bug above.
- `arr-quality-guard.nix` `anime_series_type`: Jellyseerr adds every series as seriesType `standard`, which parses season/episode tokens only. Anime fansub releases carry absolute episode numbers and group tags, so Sonarr matched none of them: Death Note, JoJo's Bizarre Adventure and Neon Genesis Evangelion each sat at 0 episodes with every release rejected "Unable to parse release" or "Unknown Series" (2026-09-02). Setting type `anime` turns on absolute numbering and the scene mappings those releases need; Death Note went 0 to 4 accepted releases the moment it flipped. Keyed on the TVDB **"Anime"** genre, not "Animation": the narrower tag hits exactly those three and leaves Futurama, Avatar and Gravity Falls standard, which is what they want.
- `arr-quality-guard.nix` / `nixflix.nix` sonarr cap 50 to 150 MB/min (2026-09-02): 50 size-rejected every release for whole shows, not just fat ones. Atmos WEB-DL runs ~75 MB/min (Shrinking S03: all 11 episodes rejected, 1 of 33 on disk) and BluRay anime ~200 (Evangelion: 0 of 26, the only valid full-season pack was 37.8 GB). Raising `max` is safe because `preferred` (12) is what ranks: Sonarr scores by closeness to preferred, so a small release still wins whenever one exists, and the ceiling only matters when nothing smaller does. Verified on Evangelion, where every smaller candidate was a movie, artbook, fancut or unparseable rip.
- `ocw-courses.nix`: deliberately **not** `wantedBy = multi-user.target`. `switch-to-configuration` starts newly-wanted units and waits for them, so a oneshot downloading tens of GB holds the activation lock for hours and every later deploy fails "Could not acquire lock". The timer is the only thing that starts it. Its selection also drops a second naming scheme: 6.002 publishes the same 26 lectures twice (`mit-6.002-lec1-...` and `ocw-6.002-lec-mit-10250-...`), which landed every lecture twice.
- `arr-autosearch.nix` retries FAILED Jellyseerr requests: its push to the arr has a 10 s timeout that this box exceeds under load, and nothing else ever retries, so a transient timeout stranded a request permanently.
- `hosts/gs-pi4/default.nix` `quotaGiB`: 192 to 256 on 2026-08-25 after the cap filled and blocked every write with EDQUOT. The unquota'd `snapshot` subvolume (T480s `/home` backups, ~113 GiB) shares the 460G drive, leaving ~87 GiB at worst; incremental sends fit, a full re-send would not.
- Every disk guard reads the media qgroup, never `df` (`media-free.nix`, suite `media-free`). `df` reports the whole 460G filesystem while the qgroup caps writes far below: on 2026-08-25 the cap was full, `df` said 151 GiB free, and every fetcher wrote until EDQUOT. An unreadable listing reads as `unknown` and holds fetchers off. **Janitorr stays filesystem-based and cannot be fixed from the host** (it statfs's inside its container); only its tile is honest.
- `nixflix.nix` `downloadarr.qbittorrent.tvImportedCategory` / `movieImportedCategory` + `qbit-seed-reap.nix` (suite `qbit-seed-reap`): **an arr re-scans every torrent left in its own category, forever.** `ProcessMonitoredDownloads` runs about every minute, `RequiresDiskAccess`, and enumerates the whole `tvCategory`; anything it cannot finish importing is retried on every pass. On 2026-09-18 that was 415 torrents with 10 permanently unimportable groups among them (140 queue records, all warnings), so the Pi re-read season-pack files off the single USB disk every minute: I/O pressure 46-71% full, load 19, sshd failing at banner exchange, arr ports refusing. CPU full pressure was **0** the whole time, which is the tell that it is disk, not work. Post-import categories take an imported download out of that scan ("Sonarr will not remove torrents in that category even if seeding finished"), and the reaper deletes it with `deleteFiles=true` once the ratio-2 / 30-day goal in `serverConfig` is met. Effect, same box, ~20 min apart: I/O full avg60 62.7% to 12.8%, load 11.9 to 2.3, queue 140 records to 0.
- **decluttarr cannot dig the box out of this, and that is the part that hid it for 12 days.** Its `remove_failed_imports` already matches these items ("One or more episodes expected in this release were not imported or missing from the release"), but the per-job queue fetch is hardcoded to 15 s in v2.1.0, so on a stalled box it times out mid-run and the container exits before any strike lands: restart counter was at **171**. The healer needs the box healthy to heal the box. After the fix it completes runs again ("Running jobs on Sonarr").
- Defining `torrentClients.qbittorrent.categories` **replaces** nixflix's default (one category per enabled arr) and `categories.json` is authoritative on a qbit restart, so any category left out is deleted from qBittorrent. Restate all of them. Both `*-imported` categories deliberately share the save path of their source category: AutoTMM is on, so a differing path would relocate the data the moment an arr recategorises a download.
- The four shapes a stuck import takes, and the right fix for each (all four were live on 2026-09-18): a season pack whose first file is named after the whole season parses as a full-season file and is refused forever ("Single episode file contains all episodes in seasons") — fix with `POST /command ManualImport`, `importMode: "copy"`, `episodeIds` overridden to the one real episode; a pack whose every episode already has a file ("Episode file on disk contains more episodes than this file contains") — `DELETE /queue/bulk?removeFromClient=false&changeCategory=true`, which keeps the seed and hands it to the imported category; a release that cannot ever satisfy the season (the live-action Avatar remake, 7 files against 20 episodes) — remove with files, `blocklist=true&skipRedownload=true`, then grab a correct pack by hand; and a malware release ("Caution: Found executable file") — remove with files, `blocklist=true`, `skipRedownload=false`.
- **Delete the download before deleting the files it imported.** Deleting the episodefiles first just hands the next retry pass something to re-import: the seven live-action Avatar files came back with fresh ids (1079-1085 to 1801-1807) within a minute. Queue removal first, then `DELETE /episodefile/<id>`.
- `ManualImport` needs a real `quality`: `Execute` applies the caller's value verbatim, with no unknown-fallback (only the `POST /manualimport` *reprocess* path fills an Unknown in). Reprocess the single file first with `quality.quality.id = 0`, take the parsed quality and languages from the reply, then send the command with those. A full `GET /manualimport?folder=...` also works but takes ~2 min per pack on a loaded box, and `filterExistingFiles=true` does **not** filter here (every file comes back, each with a rejection).
- qBittorrent 5.2.3 `POST /torrents/setShareLimits` **requires `shareLimitAction`** (400 "Missing required parameters: shareLimitAction" otherwise) and silently leaves the old limits in place if you omit it. Also note a `queuedUP` torrent is not evaluated against its share limits at all: to test a limit, pick one that is `uploading`/`stalledUP`.
- `nixflix.nix` `systemd.services.{sonarr,radarr,prowlarr}.serviceConfig.MemoryLow`: 3.7 GiB of RAM against this stack keeps zram permanently full, so every idle service is paged out and the arrs pay it as **first-call latency**, not throughput. Sonarr held 156 MiB resident against 400 MiB swapped; a cold `GET /history` took 9-11 s and the next 0.2 s. Two things silently break on that alone: decluttarr's per-job queue fetch is hardcoded to 15 s (v2.1.0), so it times out, the container exits, and its 3-strike counter never reaches a removal, and recyclarr's nightly sync dies on "HTTP 500: database is locked" or "request was canceled due to the configured HttpClient.Timeout". With the floors in place recyclarr's whole run went 3 min-and-failing to 23 s, and `arr-quality-guard` 100 s-and-timing-out to 3.7 s. `MemoryLow` is a soft floor: the kernel can still reclaim past it and it can never OOM-kill anything. Jellyfin and immich are left unprotected on purpose, since they are the largest swap tenants (~1.5 GiB each) and being paged out while idle is correct for them.
- A load spike right after a deploy is usually not a regression: restarting the arrs makes all three run their startup tasks (RssSync, ImportListSync, UpdateSceneMapping) with cold caches, and `pia-wg-healthcheck` stops qBittorrent whenever it refreshes the tunnel, which makes it flush resume data for ~450 torrents. Both together took load to 19 for a few minutes on 2026-09-19 and then decayed to 2.3 with no action. Check `Refresh Monitored Downloads` duration in `GET /system/task` before concluding the import-retry stall is back: it is 0.67 s healthy, 22-124 s when it is not.
