# sway

## kittyCwdWindow (home.nix)

Open a new kitty OS window in the focused kitty's cwd. Left Alt is the sway modifier (Mod3), so kitty can't bind it internally; this drives kitty's control socket instead. Falls back to a plain kitty when the focus is not a kitty (no socket).

## customKeymap (home.nix)

Remap left alt → Hyper_L in Mod3 so it is the sole sway modifier. Mod3 is otherwise unused; this isolates it from Win (Mod4/Super) and right alt (Mod1/Alt_R). Right alt passes through to applications as a normal Alt key. Caps → Escape is embedded here instead of xkb_options.

## Workarounds

- `home.nix` refresh signals target `waybar.service`'s main process using `systemctl --user kill --kill-whom=main --signal=RTMIN+N`. Exact `pkill -x waybar` misses the wrapped `.waybar-wrapped` process; substring matching could also signal helper scripts. Brightness keys explicitly select the backlight class, matching the bar rather than enumerating unrelated LED devices.
- `default.nix` `env_keep`: sudo strips `WAYLAND_DISPLAY` and `XDG_RUNTIME_DIR`, so Qt falls back to xcb and Xwayland rejects root. Keeping both lets `sudo <gui-app>` reach the sway socket; root-owned files can land in `/run/user/<uid>`.
- `home.nix` `xwayland force` + `xhost +si:localuser:root`: Xwayland trusts only the session user, and lazy Xwayland exits after 10 idle seconds and loses any grant. Forcing it keeps root's grant, so X11-only apps work under sudo. `xwayland` changes apply only at sway launch.
- `home.nix` `inhibit_idle fullscreen` for `steam_app_*` and `steam` windows: sway resets its idle timer only on libinput seat events, and libinput does not handle joysticks, so gamepad play locked the screen. Proton/XWayland games' X11 screensaver inhibition also never reaches Wayland idle inhibitors.
- `home.nix` customKeymap: Left Alt becomes `Hyper_L`/Mod3 because sway can't tell left/right Alt apart while both are Mod1.
- kitty caches a kitten module for the life of the kitty process: `grab.py` does `import _grab_ui`, so a second run inside the same window reuses the first `sys.modules` entry even when the map now points at a different store path. Testing a rebuilt kitten therefore needs a **new kitty instance**, not just a fresh invocation; a changed build that behaves exactly like the old one is this, not a failed edit. Drive a test instance with `kitten @ --to <socket> action kitten <store path>/grab.py` plus `kitten @ send-key` (`send-text` does not reach an overlay kitten), and read the result with `wl-paste`.
- `home.nix` `kittyCwdWindow` (Mod3+Shift+Return): sway consumes Mod3 combos before apps see them, so kitty can't bind left-Alt; the new-window-in-cwd action runs at sway level and reads the focused kitty's cwd via its control socket (`kitty.nix` `listen_on`).
- External modes: sway stores every applied output state as a per-output config, current mode included (`output_config_for_config_head` in sway's `desktop/output.c`), and re-applies it when that connector reappears. After an S3 resume on 2026-10-13 the dock brought the monitor back as DP-5 before its EDID was readable; it sat at 640x480, sway stored that, and the reconnect 7 s later re-applied 640x480 although the real EDID (1920x1080@100) was there by then. way-displays re-applies the preferred mode on every head change, which should overwrite a stale stored mode; the old dedicated DRM-uevent guard was dropped with kanshi, unverified against a real resume. wlroots 0.20 re-reads a connector's modes only on a disconnect/connect or a bad link, never for an EDID that arrives late on a still-connected output, so that case still needs a replug.
- CPU hover also shows online P/E/LP-E logical-CPU counts and per-type average reported frequency without widening the bar. P/E membership comes from the kernel's `cpu_core`/`cpu_atom` PMU lists; on the verified X7 358H, Atom CPUs with a 1.5 GHz nominal `base_frequency` are LP-E. Do not classify by `cpuinfo_max_freq`: passive mode with turbo disabled changes that value and previously merged LP-E into E. All current frequencies are sampled in one pass at the existing 10 s interval.
- Steam Remote Play (T480s client): works fine under sway/XWayland (verified 2026-07-02); the old white-screen/~1FPS was guest-side (wedged tailscale + RX580 Code 43), not the client display chain. Do NOT set `LIBGL_DRI3_DISABLE=1`; it forces llvmpipe and breaks Steam launch entirely.
- `home.nix` `--locked ${mod}+Shift+x`: the lock binding is `--locked` so the same key recovers an orphaned lock without a TTY; sway still routes `--locked` bindings while the session is locked.
- `default.nix` enables Hyprlock with password-only PAM (`security.pam.services.hyprlock.fprintAuth = false`); native fprintd authentication scans automatically alongside the password prompt. PAM must not also claim the reader. George verified both fingerprint and password unlocks in a nested sway preview. With the lid closed the password remains available immediately; the inaccessible reader cannot impose the old PAM fingerprint timeout.
