# gs-framework-13-pro

## Workarounds

- `default.nix` overrides the inherited policy: `keep-outputs = false`, `keep-derivations = false`, weekly `nix-collect-garbage --delete-old`. Latest successful target builds are rooted separately at `/etc/nixos/.gcroots/<target>` by the Makefile; current and booted systems plus the current independent known-good profile remain protected. Framework direnv loads flake shells without persistent profiles/input roots, so project environments may need downloading or rebuilding after GC. Use the retained build commands in `README.md`; direct `nixos-rebuild` does not advance those target roots.
- `default.nix` `fbcon=font:VGA8x16`: xe takes over the console after `systemd-vconsole-setup`, which resets `console.font` to the kernel's 16x32 default, so the size is set in the kernel.
- `default.nix` `ttm.page_pool_size=131072`: the TTM pool otherwise keeps freed GPU pages up to half of RAM, Vulkan reports them as used, and Ollama puts part of the next model load on the CPU. The limit must be set at boot; writing the sysfs parameter at runtime has no effect.
- Moving the SSD from the T480s (2026-10-19) kept the OS but not state tied to the old hardware. NetworkManager profiles were pinned to the old card (`connection.interface-name wlp61s0`, two by `802-11-wireless.mac-address`), so they silently never matched the new `wlp0s20f3` and NM created `<name> 1` duplicates when George re-entered keys; pins are now cleared, so a future card swap is a non-event. Bluetooth pairings are keyed by the adapter address and must be re-paired. libvirtd failed with "TPM key integrity check failed": `virt-secret-init-encryption` seals `/var/lib/libvirt/secrets/secrets-encryption-key` to the TPM, so it was deleted to be regenerated for the new one. The RTC came up at 2025-01-01, which only produced "persistent file timestamp in the future" timer warnings and one failed `gs-pi4-state-pull`; NTP corrected it.
- `default.nix` `iphone-usb`: the home LAN has no IPv6 default route, so a USB-tethered iPhone became the only IPv6 exit and carried all IPv6 traffic even with Ethernet up. A route metric cannot fix that, because no other IPv6 default exists; the profile sets `ipv6.never-default` and ranks IPv4 below Wi-Fi.
- `default.nix` `services.hardware.bolt.enable`: both USB4 domains report security level `user`, so without boltd a Thunderbolt dock's PCIe tunnel is never authorized.
- `power.nix` swap: one 32 GiB swapfile at `/swap/swapfile` in a dedicated `@swap` subvolume (a swapfile cannot live in a subvolume that gets snapshotted). The old 16 GiB `nvme0n1p2` partition sits directly before the Btrfs partition, so growing it would mean moving root; it is left on disk unused, and the known-good boot entry still references it. Hibernate resumes from the Btrfs device at `resume_offset`, the value `btrfs inspect-internal map-swapfile -r` printed when the file was created. Recreating the file moves it; `swapfile-resume-offset-check.service` then fails, and `resumeOffset` must be updated or resume will miss the image.
- Battery: idle draw measured 7.5 W at 30% brightness with C10 residency 80%, about 10 h from the 74 Wh pack; 60 Hz versus 120 Hz measured no difference (7.6 vs 7.5 W). Short-window estimates while building read 10-11 W and project ~6.5 h.
- [Framework's published battery tests](https://frame.work/ca/en/laptop13pro): 20 h Netflix 4K, 17 h active web use and 11 h conferencing. The Netflix footnote specifies X7 358H, Arc B390, 32 GB RAM, 1 TB storage, 250-nit brightness, 60 Hz, Wi-Fi on, volume 30%, Dolby Atmos off, Windows 11 Netflix app and Best Power Efficiency mode. A 74 Wh pack over 20 h implies 3.7 W average; our ~7 W background-work samples are not an equivalent workload or evidence of the hardware's runtime ceiling. Brightness percentage is not calibrated nits.
- `power.nix`: `TLP_AUTO_SWITCH=1`, `TLP_PROFILE_AC=PRF` and `TLP_PROFILE_BAT=SAV` select performance on AC and power-saver on battery, including after resume. Saver uses EPP `power`, turbo off, firmware `low-power`, PCIe `powersupersave` and xe `power_saving`; AC retains EPP/firmware `performance` and turbo. Manual balanced remains available until the next automatic source/resume switch. `tlpctl` acknowledges before hardware settles, so verify the actual sysfs values after the transition. No fixed runtime gain is assumed; the earlier platform/ASPM sample was 8.31 W to 6.93 W and the separate post-switch sample 7.27 W.
- `power.nix` energy-aware scheduling (EAS) on battery only: power-saver switches `intel_pstate` to passive mode (`intel_cpufreq`) with the `schedutil` governor, the documented precondition for EAS on hybrid CPUs without SMT. The kernel then registers an energy model for all 16 CPUs and `kernel.sched_energy_aware` reads 1, so light tasks are placed on the cheapest capable cores (LP-E/E) instead of merely any core with spare capacity. EPP `power` and turbo-off still apply in passive mode. AC and manual balanced are pinned to active mode with `powersave`, unchanged from before; verified by forcing `tlp power-saver` then `tlp performance` on AC, and TLP selected passive mode by itself on a real unplug. A 2026-10-28 on-battery old/new/old/new A/B (90 s rounds, 20 s settle, same EPP and turbo-off, quiet desktop) measured old 7.01 and 8.05 W, new 7.30 and 6.68 W: means 7.53 vs 6.99 W, but the spread within each setting exceeds the difference, so no saving is established. No regression was seen either; a longer real-use comparison is needed before claiming a gain.
- eDP-1 stays at 120 Hz with adaptive sync disabled: enabling sway adaptive sync was accepted by the panel but George observed choppy cursor movement. Do not re-enable it solely because the reported status is `enabled`. Scale is 1.75 (logical 1645x1097), chosen by George after a live trial at 2.
- `power.nix` `HandleLidSwitchExternalPower = "lock"`: closing the lid on AC locks and keeps running, so builds, downloads and local inference continue (an overnight lid-closed `ollama pull` made no progress under the logind default, which suspends). On battery the lid still suspends. A suspend freezes every process, `nix build` included.
- Charge limit: set to 80% in the Framework BIOS and read back as `BAT1/charge_control_end_threshold`. On this host TLP picks its `generic` battery plugin (the `framework_laptop` driver overrides `cros-ec` detection) and cannot set thresholds. The shared upower tmpfiles rule stays, since upower's own limit would otherwise rewrite the BIOS value at startup.
- Controlled bar on/off/on on battery, power-saver, fixed 120 Hz and the same static Kitty window: 4.02 W initially settling, 3.18 W with bar stopped (3.09-3.35), 3.53 W with bar restored (3.39-3.69). The later comparison suggests ~0.35 W for the bar, not the whole ~7.8 W seen during active agent/render/build work. These are short quiet-workload measurements, not a browsing/video runtime claim.
- 2026-10-28 post-update audit: the running Waybar 0.15.0 derivation still includes the title-event patch, and deployed polling intervals remain unchanged. A 30.05 s cgroup sample used 1.275 CPU-seconds (4.24% of one core), including all helper processes; this is not comparable to the older Waybar-process-only 0.9% figure. The corrected P/E/LP-E CPU tooltip used a median 95 ms CPU per refresh over five calls on battery (about 0.95% of one core at its 10 s interval). These CPU measurements are not a fresh battery-watt attribution.
- Firefox playback proof: the installed Firefox 157 with managed VA-API preferences decoded real H.264 and AV1 clips using `FFmpegVideoDecoder` with `IsHardwareAccelerated=true`, advancing frames and no dropped frames, on an isolated native Wayland output using the real GPU. Media-GT residency changed with playback, but other apps were running so it is supporting evidence, not exclusive attribution. User-activated unmuted fullscreen playback created a Wayland idle inhibitor; a harmless 3 s idle marker stayed absent until pause. Muted/video-only playback did not inhibit in that test. No claim is made about personal tabs/site codecs or physical-panel scanout.
- The dual-USB-C AV Access iDock C20 is a [5 Gb/s USB-C/DisplayPort Alt Mode KVM](https://www.avaccess.com/products/idock-c20-kvm-switch-docking-station/), not a Thunderbolt dock. The live topology has no external Thunderbolt router. The Brio 101 is on its shared USB 2.0 branch; 90-frame VGA YUYV, 1080p MJPEG and 720p MJPEG streams all opened successfully on the Framework and were discarded to `/dev/null`. The reported historical camera failure occurred on the T480s; its cause is not established by these successful current tests.
- Framework non-interactive root commands use `sudo-notify <command> [arguments...]` from `default.nix`. It execs `pkexec`, so the polkit-gnome dialog names the command before authentication. `security.polkit.enablePkexecWrapper` supplies the setuid wrapper. polkit grants no cached approval, so each command prompts; `pkexec` also clears the environment and starts in root's home, so pass absolute paths. Plain `sudo nix-clean` applies the Framework GC policy without flags; the distinct name avoids Nix development shells shadowing the system command.
- `fingerprint-led.nix` loads `ledtrig_timer`: the `timer` trigger is a module, and without it `chromeos:white:power` offers no blink trigger, so writing `timer` fails with EINVAL. The service hands the LED back to the EC with `chromeos-auto` after each verify and on stop.
- `fingerprint-lid.nix`: the reader is in the lid, so with it closed every fingerprint-enabled PAM service waited out pam_fprintd's ~30 s timeout before the password prompt. A `pam_exec` rule at the fprintd order minus 100, `[success=1 default=ignore]`, skips exactly the next line when any `/proc/acpi/button/lid/*/state` reads closed. It extends the PAM service submodule, so it lands in all 23 services that carry an `fprintd` rule; `greetd` has `fprintAuth` but delegates to `login`, so the rule is keyed on the fprintd rule existing, never on `fprintAuth`, or it would skip the whole `login` substack. A failing check is ignored, leaving the normal fingerprint-then-password order. Verified lid closed: 30 s fingerprint timeout before, password prompt in 4.7 s after.
- `default.nix` console font: `ter-v16n` replaces the forced 32-pixel font for compact boot text on docked displays. `earlySetup` includes it in the initrd. Actual boot-time clipping must be checked on the physical display; a successful build does not prove console geometry.
- `default.nix` selects `pkgs.ollama-vulkan`, enables the iGPU with `OLLAMA_IGPU_ENABLE=1` and selects one B390 device with `GGML_VK_VISIBLE_DEVICES=0` (Mesa exposes duplicate ICD entries). `ollama ps` reports `100% GPU` and logs show 31/31 layers offloaded. Warm Vulkan smoke with a 2061-token uncached prompt and 64 generated tokens: Gemma 26B QAT ~342 prompt / 24 generation tok/s, abliterated 26B ~246 / 20; cold startup/shader compilation is slower. `vulkan-tools` is installed on this host for `vulkaninfo --summary`.
- GPU placement is memory-dependent, not guaranteed by selecting Vulkan: the abliterated 26B fitted fully on the B390 in isolation, but after a full-context agent run the deployed service selected 41% GPU, then 81% after an explicit unload/reload. Both direct `ollama run --think=false` smoke requests returned `CHAT_OK`. Inspect `ollama ps` for actual placement; do not force all layers onto the GPU when shared RAM is constrained.
- `default.nix` `virtualisation.oci-containers.containers.open-webui`: official [Open WebUI v0.12.4](https://github.com/open-webui/open-webui/releases/tag/v0.12.4), pinned by release tag and GHCR OCI index digest, runs as `podman-open-webui.service`. Host networking reaches the existing Ollama at `127.0.0.1:11434`; upstream `start.sh` honors `HOST=127.0.0.1` and `PORT=18080`, keeping chat at `http://localhost:18080` without LAN exposure or a firewall opening. The standard image does not bundle Ollama. No Docker socket, host shell, privileged mode or GPU mount is supplied.
- Open WebUI state remains `/var/lib/open-webui` (the native service's symlink into `/var/lib/private/open-webui`); the resolved private directory is bind-mounted at `/var/lib/open-webui` inside the container, avoiding reliance on source-symlink traversal. `DATA_DIR` keeps `data/webui.db`, uploads and vector data; the native static and model-cache paths remain unchanged. The existing `.webui_secret_key` is separately bind-mounted read-only at `/app/backend/.webui_secret_key`; `WEBUI_SECRET_KEY_FILE` makes `start.sh` load it, and a missing source fails the bind instead of generating replacement credentials. The official image runs as `0:0` (non-root configurations are explicitly untested upstream); all capabilities are dropped except `DAC_OVERRIDE`, needed for the retained DynamicUser-owned files, with `no-new-privileges`. No ownership migration or Ollama model move is needed.
- Before the native-to-container cutover, stop `open-webui.service`, confirm the existing `data/webui.db` and `.webui_secret_key` are regular nonempty files without printing them, then take both an SQLite backup and a root-private full backup of the resolved state directory, including the key, uploads, vector store and caches. Keep the backup outside that directory. Switch only after the backup succeeds; never run the native and container writers together. Before every later image update, stop `podman-open-webui.service` and take the same backups: application startup can migrate the schema, so rolling back only the image/system generation is not enough; restore the corresponding state backup too.
- Open WebUI updates are independent of `nix flake update`: check GitHub `releases/latest` for the latest stable tag, resolve its official `ghcr.io/open-webui/open-webui` OCI index digest, update both parts of `image`, then rebuild/switch. No native Open WebUI/Python source dependency overrides remain. Check `curl --fail http://127.0.0.1:18080/health`, `curl --fail http://127.0.0.1:18080/api/version`, the listening address with `ss -ltnp`, existing login/chats/settings, and Ollama model access after activation. Environment defaults only seed first-run database config; existing DB rows remain authoritative. Web search uses DuckDuckGo via `ddgs` (queries leave the machine); use Admin Settings for changes, and the chat's Web Search toggle for the model's native `web_search` tool.
